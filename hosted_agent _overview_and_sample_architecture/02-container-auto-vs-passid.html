What the "container" actually is

A Microsoft-managed sandbox that Foundry spins up on its own backend — you never provision or pay for a VM by the hour.

Managed sandbox session

A "code interpreter session" Foundry runs for you — abstracted, ephemeral.

Hyper-V isolated

A per-session micro-VM security boundary — Microsoft-managed, not one you deploy.

No outbound network

Can't pip install; a fixed set of preinstalled packages, same region as the project.

Nothing local

Not your machine, not a VM you manage. Foundry owns the host lifecycle.

AUTO container: auto

The code interpreter spins up its own container each session.

1

Tool requested with container:{type:"auto"}

No container id supplied — the service creates one on demand.

2

Service provisions a session

A fresh managed sandbox is created for that turn/conversation.

3

Python runs, files written to /mnt/data

Charts / PPTX are generated inside the sandbox.

4

...but you can't get the files back

In private Foundry the output files aren't surfaced for download.

Blocked for us: in private Foundry, file download fails — and a hosted agent's managed identity often can't even create a container (RBAC 403).
PASS-ID pre-create + pass container id

The client pre-creates the container, then hands its id to the agent. This is what we use.

1

POST /openai/v1/containers

Client (its own identity) creates the session up front → returns cntr_….

2

Pass USE_CONTAINER_ID=cntr_…

Sent in each request; the agent binds code interpreter to that exact container.

3

Agent only uses the container

Managed identity never creates one → sidesteps the RBAC 403.

4

Client downloads the files

GET /containers/{id}/files/{file_id}/content — the PPTX/chart comes back.

Works today: same managed sandbox, but because we own the id we can enumerate & download outputs and avoid the create-permission error.
So — does it use a VM?
  • Not a VM you spin up. No local VM, no AKS node, no compute you provision or pay by the hour.
  • Under the hood it's a Hyper-V-isolated micro-VM used purely as a security sandbox — created, run, and torn down by Microsoft.
  • Auto and pass-ID use the same sandbox. Pass-ID only changes who creates it and who can read the files.
Lifecycle & latency
  • Session is active up to 1 hour with a 30-min idle timeout; reused within that window.
  • Spin-up is a one-time, few-seconds cold start per session — no VM-boot minutes. After that, calls hit the warm container.
  • Pass-ID adds one extra POST /containers round-trip — negligible.

"Hyper-V isolation" describes how Microsoft sandboxes the session; it is a managed micro-VM boundary, not a virtual machine you deploy, size, or pay compute-hours for. The Azure Container Apps dynamic-session detail is an implementation note — the official docs describe it simply as a "sandboxed execution environment."
