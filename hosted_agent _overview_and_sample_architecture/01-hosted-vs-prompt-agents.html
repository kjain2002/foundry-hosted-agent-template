Hosted agents vs prompt agents

Behind the scenes — what actually runs, and why we build the hosted one with the Agent Framework

No code. You describe it; Foundry runs it on a shared, managed runtime.

H Hosted agent

We write the agent in the Microsoft Agent Framework; Foundry hosts our container.

1

We write the agent in code

Agent + FoundryChatClient + tools (MCPStreamableHTTPTool, CodeInterpreterTool), served by ResponsesHostServer.

2

Packaged & deployed to Foundry as your image/code, running under a managed identity.

3

Custom orchestration: OAuth-consent MCP via a toolbox, pre-created code-interpreter container, guardrails.

4

Gets around private limits

The control we gain is exactly what lets file download & skills work in private Foundry.

Why we chose hosted for AlignTech
  • Private Foundry blocks code-interpreter file download and skills on a prompt agent.
  • Hosted + Agent Framework gives us the control to work around those limits today.
  • Same Foundry functionality underneath — no exotic custom tools.
The trade-off
  • Hosted = we own a deployable, so there's a runtime to host (compute cost + upkeep).
  • If/when private-endpoint support ships for code interpreter, we could move back to a prompt agent.

Prompt agent = declarative agent defined by instructions + tools, run on Foundry's managed runtime. Hosted agent = an Agent Framework app packaged and deployed to Foundry (via azd or the Foundry Toolkit), running as your own container under a managed identity. Both call the same Foundry models and tools.
